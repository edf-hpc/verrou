# File formats of verrou

Specification of the files read and written by verrou and by the
`verrou_dd_*` tools, as implemented by the development version following verrou 2.7.0 (Valgrind
engine). Any implementation of verrou must read the files of this version and write files
that this version reads, except where a section says that the content depends
on the engine.

Conventions:
- a line ends with `\n`; fields are separated by one tab (`\t`) when the
  file is written by verrou; when verrou reads a file, a field separator is
  any sequence of tabs and spaces, except for the last field, which extends to
  the end of the line and can contain spaces (the other fields cannot);
- a line starting with `#` is a comment, ignored when the file is read;
- `FNNAME` is the name of a function as given by the debug information,
  **not demangled** (`_Z15testConvergenceRKf`); a function without name is
  `unamed_function_verrou`;
- `OBJNAME` is the path of the object (executable or shared library) as given
  by the debug information (absolute path for the shared libraries); an
  object without name is `unamed_object_verrou`;
- `FILENAME` is the source file name as given by the debug information
  (relative path when the program was compiled with a relative path);
- `LINE` is a decimal line number;
- `ADDR` is a decimal unsigned integer: an absolute address in the process.
- `%p` in a file name given in an option or generated by verrou is the pid of
  the process (`%q{VAR}`: value of the environment variable `VAR`).

## Exclusion file (`--exclude=`, `--gen-exclude=`)

One line per excluded symbol:

    FNNAME<TAB>OBJNAME

A `FNNAME` (or `OBJNAME`) starting with `*` matches any function (object):
`*<TAB>/usr/lib/x86_64-linux-gnu/libm.so.6` excludes the whole libm. There is
no other wildcard (`*` is not a glob: the rest of the field is ignored). With `--gen-exclude=`, the
file lists every symbol which executed a floating-point operation (one line
per symbol and object, order not specified).

## Source file (`--source=`, `--gen-source=`, `--warn-unknown-source=`)

One line per source line:

    FILENAME<TAB>LINE<TAB>FNNAME

`FNNAME` is required when the file is read. With `--gen-source=`, the file
lists every source line which executed a floating-point operation (order not
specified); the lines without floating-point operation which follow a
floating-point line in the same block are not listed.

The same format is used by the files of the cancellation and denormal
detection: `--cc-gen-file=` (lines with a cancellation), `--cdi-gen-file=`
(lines with a denormal input), `--cdo-gen-file=` (lines with a denormal
output).

## Trace inclusion file (`--trace=`)

One line per traced symbol, same fields as the exclusion file:

    FNNAME<TAB>OBJNAME

## Backtrace files (`--gen-backtrace=`, `--exclude-backtrace=`)

`--gen-backtrace=REP` writes two files in the directory `REP`:

- `backInfo-%p`: one line per distinct backtrace of a floating-point operation:

      N:ADDR1,ADDR2,...,ADDRN

  `N` (1 to 40) is the number of addresses; `ADDR1` is the innermost frame.
  This is the format read by `--exclude-backtrace=` (the lines of the
  backtraces to exclude).
- `backAddrInfo-%p`: debug information of the addresses of the backtraces,
  one line per address:

      ADDR<TAB>FNNAME_WITH_OFFSET<TAB>FILENAME<TAB>LINE

  `FNNAME_WITH_OFFSET` is the function name followed by `+offset` when the
  address is not the start of the function. Without debug information,
  `FILENAME` and `LINE` are not significant.

**Engine dependent**: the addresses are absolute addresses of the process.
They depend on the load addresses chosen by the engine (and by the kernel,
with ASLR): a `backInfo` file can only be used with the same binary, the same
engine and the same load addresses. A `backInfo` file written by one engine
is not valid for another one.

## Coverage files (`--trace-type=back_cover`, `--output-trace-rep=`)

The directory given by `--output-trace-rep=` (current directory by default)
contains:

- `backCoverInfo-%p`: one section per coverage dump (client request
  `VERROU_DUMP_COVER`, IOMatch action `dump_cover`, end of the program):

      cover-INDEX
      [BBADDR] N:ADDR1,...,ADDRN<TAB>COUNT<TAB>FIRST

  `INDEX` is the number of the dump (from 0); `BBADDR` the address of the
  block; `N:ADDR1,...` its backtrace (as in `backInfo`); `COUNT` the number of
  executions of the block with this backtrace since the previous dump;
  `FIRST` the rank of its first execution in the dump. Only the blocks
  executed since the previous dump are listed.
- `backAddrInfo-%p`: as for `--gen-backtrace=`.
- `bbAddrInfo-%p`: one line per block:

      [BBADDR] FILENAME<TAB>LINE<TAB>F|I<TAB>?|!

  `F`: the block contains a floating-point operation (`I` otherwise); `?`: the
  block contains a floating-point comparison (`!` otherwise).

**Engine dependent**: as the backtrace files, the addresses depend on the load
addresses and the blocks on the engine (a Valgrind superblock is not a
DynamoRIO basic block): `verrou_gen_trace` and `verrou_analyse_trace` must
only compare coverages of the same engine.

## Coverage files (`--trace-type=bb_cover`)

The directory given by `--output-trace-rep=` (current directory by default)
contains:

- `trace_bb_cov.log-%p`: one section per coverage dump (same triggers as
  `back_cover`):

      cover-INDEX
      BBADDR|BBINDEX:COUNT

  one line per block executed since the previous dump; `BBINDEX` is the
  number of the block given by verrou.
- `trace_bb_info.log-%p`: one line per instruction of a block:

      BBADDR|BBINDEX : FNNAME : FILENAME : LINE : 0|1 : 0|1

  the two last fields: the line contains a floating-point operation, a
  floating-point comparison.

The symbols traced are those of `--trace=`. **Engine dependent**: as
`back_cover`.

## IOMatch script (`--IOmatch-clr=`) and output (`--output-IOmatch-rep=`)

The script is a sequence of lines `KEY: VALUE` (the keys are listed in
[inventory.md](inventory.md)); its semantics is documented in the manual
(section *IOMatch*).

The log of the matches is `SCRIPT.log-%p` (`SCRIPT`: path of the script), or
`REP/IOMatch.log-%p` with `--output-IOmatch-rep=REP`. With `dump-stdout:` /
`dump-filtered-stdout:`, the copy of the output (filtered output) is
`SCRIPT.stdout-%p` (`SCRIPT.filtered.stdout-%p`), or the file name given as
value of the key, relative to `REP` if given. The log is a text file for the user: its content is not specified.

## Delta-debugging cache (`verrou_dd_*`)

The cache directory (`dd.line`, `dd.sym`, `dd.back`, `dd.stdout`, `dd.task`,
or `--rep=`) contains:

- `cmd.last`: the parameters of the last search (the previous one is renamed
  `cmd.MM-DD-YYYY_HHhMMmSSs`):

      ENV <path of the tool>:
      <TAB>VAR=VALUE                    (one line per VERROU_DD_* / INTERFLOP_DD_* variable)
      ENV VERROU:
      <TAB>VAR=VALUE                    (one line per VERROU_* variable)
      Cwd: <working directory>
      Cmd: <command line, each argument quoted for the shell>
      TimeStamp: MM-DD-YYYY_HHhMMmSSs

      arg: <absolute path of the run or cmp script> (md5=<md5 of its content>)
      --begin content--               (only for a script of less than 100 lines)
      <content of the script>
      --end content--

  `post_verrou_dd` and `verrou_dd_metamodel` read `Cwd:`, `Cmd:` and the
  `ENV VERROU:` variables.
- `ref/`: the reference run (`--reference-rounding=`), with the search space
  generated by verrou (`dd.line`, `dd.sym`, `dd.back`... in the format of the
  generation option: source file, exclusion file, backtrace file), and
  `dd.out` / `dd.err` / `checkRef.out` / `checkRef.err`.
- one directory per configuration tested, named by the md5 of the sorted
  deltas (each preceded by `\n`; md5 of the empty string for no delta): `dd.<space>.include` / `dd.<space>.exclude` (the deltas perturbed /
  not perturbed, same format as the search space), and `dd.runN/` for each
  sample `N`, which contains the output of the run script, `dd.run.time`
  (duration in seconds), `dd.compare` (output of the comparison script) and
  `dd.return.value` (first line: return code of the comparison script,
  0 when the run is valid).
- relative symbolic links to the result configurations: `ddmin0`, `ddmin1`, ... (minimal
  failing sets), `rddmin-cmp` (complement), `ddmax`, `ddmax-cmp`,
  `FullPerturbation`, `NoPerturbation`.
- `rddmin_summary`: one paragraph per `ddminN`:

      ddminN:<TAB>Fail Ratio: XX.XX%<TAB>Fail indexes: I1,I2,...
      <TAB><description of a delta>     (one line per delta of the set)

The content of the outputs of the run and comparison scripts belongs to the
user. The search space files depend on the engine as the corresponding
generation option: the source and symbol spaces are portable (debug
information), the backtrace space is not (addresses).
